# HERO Logistics — Customer Portal Source of Truth

## Purpose

This document is the implementation source of truth for the **Customer Portal** in the HERO Logistics SaaS platform.

The Customer Portal is not an internal operations portal. It is the transport company's client-facing portal where a customer can:

- request transport
- view and track its own loads
- access PODs and customer-visible documents
- view invoices and make payments
- communicate with Dispatch / Accounts / Support
- manage users inside its own customer organisation

The Customer Portal must never become a Dispatcher, Driver, Warehouse, Yard, Accounts, or Company Admin portal.

# 4. Required Data Isolation

Every customer-facing read and write must be scoped by:

```text
companyId / tenantId
+
customerAccountId
```

Conceptually:

```text
WHERE companyId = authenticatedCompanyId
AND customerAccountId = authenticatedCustomerAccountId
```

Changing a URL ID must never expose another customer's:

- loads
- bookings
- invoices
- payments
- documents
- messages
- support tickets
- users
- activity logs

Backend enforcement is mandatory. Frontend filtering alone is not security.

# 10. BookingRequest and Load Must Be Separate Concepts

Do not blindly use one object for both request and operational load.

Recommended relationship:

```text
BookingRequest
    |
    +-- convertedToLoadId
              ↓
             Load
```

This allows proper handling of:

```text
Draft
Submitted
Under Review
Need More Information
Confirmed
Converted to Load
Rejected
Cancelled
Expired
```

Customer should be able to see clear transitions such as:

```text
Booking Submitted
→ Awaiting Dispatch Review

Booking Confirmed
→ Load LD-3987 Created
```

# 11. Booking Change and Cancellation Rules

## Before confirmation

Customer may edit draft/request data if allowed.

## Submitted / Under Review

Customer may update or cancel the request according to policy.

## Confirmed but not dispatched

Use a controlled **Request Change** / **Cancellation Request** flow.

Potential changes:

```text
Pickup date
Delivery address
Items
Special instructions
Contact information
```

These should be approved/reconciled by Dispatch where operational impact exists.

## Picked up / In Transit

Normal direct cancellation or structural editing must be blocked.

Customer should contact Dispatch.

# 36. Critical Audit Checklist

Before calling the Customer Portal production-ready, verify:

1. Dashboard and Invoices & Payments totals reconcile.
2. Dashboard payment totals match Accounts payment data.
3. Booking submission creates a BookingRequest, not a production Load directly.
4. Dispatch controls conversion from BookingRequest to Load.
5. Customer cannot mutate operational Load statuses.
6. My Loads reads real shared Load records.
7. Customer tracking reads real permitted tracking data.
8. Customer can only access own `customerAccountId`.
9. URL tampering cannot access another customer.
10. POD is the same shared POD record created by operations.
11. Internal-only documents never leak to Customer Portal.
12. Invoice is the same shared Invoice record used by Accounts.
13. Payment flow uses real provider/backend reconciliation.
14. Payment webhooks are authenticated/idempotent where applicable.
15. Partial payments update invoice balances correctly.
16. Messages can link to load/booking/invoice context.
17. Support tickets are distinct from operational messages.
18. Customer-side `Accounts User` naming is clarified to Billing User if appropriate.
19. Customer Admin can only manage users within own customer account.
20. Dashboard cards/charts are not hard-coded demo metrics.
21. Authenticated user/account identity is used consistently.
22. No customer action can create internal operational users.
23. Cross-portal changes propagate from one domain source, not copied state.
24. Audit/activity logs capture privileged actions.
25. Existing UI theme and navigation remain intact unless change is required by this specification.

# 38. Implementation Principle

Do not rebuild the Customer Portal from scratch if the current UI already exists.

The correct implementation approach is:

```text
AUDIT EXISTING CODE
    ↓
IDENTIFY CURRENT DATA SOURCES
    ↓
REMOVE MOCK / DUPLICATE STATE
    ↓
CONNECT REAL DOMAIN RECORDS
    ↓
ENFORCE BACKEND RBAC + CUSTOMER ISOLATION
    ↓
FIX WORKFLOW CONNECTIONS
    ↓
VERIFY CROSS-PORTAL EFFECTS
    ↓
RUN END-TO-END TESTS
```

Preserve the current visual theme unless a UI change is necessary to support the locked workflow above.
